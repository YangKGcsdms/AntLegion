# 协议 v3.0 可行性验证与实现评估（2026-08）

用十二个真正隔离的操作系统进程对着一条日志跑，验证 `PROTOCOL.md` v3.0 的主张是否成立，
并评估当前实现方式的问题。装置：`antlegion-bus/examples/mock-colony/`，一条命令可复现：

```bash
cd antlegion-bus && npx tsx examples/mock-colony/colony.ts
```

## 一、为什么要重做装置

仓库里已有四个 `scenario-*.ts`。它们确实走真实 HTTP，但**所有客户端跑在同一个 Node 进程
里** —— 一个事件循环、一个时钟、一个 fetch 栈、一个崩溃域。

这对本协议是个致命的取样偏差：协议的核心主张是「什么都不共享的 agent 能折出同一个世界」，
而共享的事件循环把协议承诺去仲裁的东西**提前串行化**了。两个协程不会真的同时发起 claim；
一个进程里的两个客户端也不会有各自漂移的时钟。用它验互斥，等于用单线程验锁。

新装置把每个 agent 拉成独立进程，只交给它两件事：总线 URL 和自己的名字。没有任务清单、
没有同伴名单、没有阶段表、没有停止信号。

**阶段本身是日志上的一个 subject 寄存器**，每个 agent 自己折出来。这一点是有意的：如果
「用事实日志协调互不相识的进程」不成立，这个 harness 连跑都跑不起来。它跑起来了。

## 二、结果

十二个 agent（4 worker / 2 sensor / 2 auditor / 1 crasher / 1 mallory / 1 retractor /
1 chainer）+ 1 条总线进程，Δ=4s，逐条 fsync。连跑三轮，每轮约 206–215 条事实。

| § | 主张 | 结果 |
|---|---|---|
| §9.1 | 互斥性 | **24/24 完成，0 重复**。5 个 agent 争抢，没有任何任务被两个 agent 认定赢下 |
| §8.4 §9.3 | 崩溃重分派 | crasher 握着 2 个 claim 死掉 → **2/2 失效后被别人完成**；已完成的 resolve 无一被撤销 |
| §9.4 | 幂等性 | **4/4 worker** 观察到逐字节重发返回同一个 `seq` 且 `deduped` |
| §5 | 字段值域 | 非有限 `ts` / 非法 `type` / 空 `refs` 值 / 两个生命周期 ref / 数组 payload —— **5/5 被总线以 400 拒绝** |
| §10.1 | 折叠门控 | 陌生人的墓碑、陌生人的 supersede、对未领取事实的 resolve、未持有的 release —— **总线 4/4 接受**（它不判断含义），**读者 4/4 不采信** |
| §8.1 | 寄存器 | 被撤回的头部折叠为 `null`；5/5 sensor 寄存器仍折出值 |
| §8.2 | 踪迹 | 5 层链无缺口；未解析祖先给出显式缺口标记 |
| §9.2 §11.1 | 跨崩溃确定性 | SIGKILL 总线 → 从日志重放 → 钉住同一 head 再折 → **哈希逐字节相同**；`id_failures=0`、`sig_failures=0`、无撕裂尾 |

数字上值得单说的一条：**25 条 resolve 事实对应 24 个任务**。多出来的那条是 mallory 对一条
从未被领取的事实发的 resolve —— 它**上了链**（总线不判断含义），但**没有被任何折叠采信**
（那条事实仍折为 `open`）。这一条同时演示了协议的两半：总线只管定序和保存，含义由读者决定。

## 三、实现方式总结

一句话：**可信核心极小，含义全在读者的纯函数里，靠内容寻址与全序把「同意」变成算术。**

- **总线**（`bus.ts`，200 行）只做四件事：赋 `seq`、盖 `recv`、签名、持久化并提供区间读。
  它唯一的派生索引（seq 计数器、`id→seq` 去重表）是日志的纯投影。没有逐事实可变状态。
- **折叠**（`fold.ts`）是含义所在，全是对事实流的纯函数。四问对应四条折叠。
- **客户端**（`client.ts`）在传输之上做「追加—读回—折叠」的封装，`alctl` 与 `ant`、`dsh`
  都走同一套折叠，所以折叠逻辑只写一遍。
- **互操作契约是向量集而不是散文**（`conformance/vectors.json`），且 `verify.py` 用独立
  Python 实现复现折叠输出而不只是哈希。

这个结构的好处在这次验证里是可见的：崩溃恢复没有状态机要重建（日志就是状态）；「谁赢了」
不需要任何一方问任何人；总线接受一条恶意事实与读者拒绝采信它，是两件互不干扰的事。

## 四、评估：发现的问题

### 4.1 已修复的三个实现缺口

**(1) Δ 不可由运维配置** —— §B 说 Δ「由日志设定」、§7.5 说总线 MUST 暴露生效值。它确实
暴露了，却没有任何办法被告知该是多少：唯一的入口是 `BusV2` 构造函数。跑 `node dist/index.js`
的人永远卡在 600s。也就是说「Δ 是日志的属性」这句话在规范里为真、在命令行上为假。
已补 `ANTLEGION_CLAIM_TIMEOUT`，并补了「非法值回退到 §B 默认」的测试。

**(2) `colony()` 没有实现 §8.5 的离场规则** —— 规范写明「排除最新注册已被撤回的作者 ——
智能体就是这样离场的」，实现从未做这件事。写 dsh 的 liveness 测试时撞出来的。已补上，并
区分清楚：必须是**最新**那条被撤回才算离场；撤回更早的注册是常规家务（让 §11.2 能回收
payload），不该把人踢出名册。

**(3) §8.1 规则 4 的理由过度声称** —— 这是这次多进程验证直接打出来的。规则 4 说作者门控
「堵住了一个劫持：未加门控的 `supersedes` 让任何作者一次追加就能让任何事实的信任状态噤声」。
实测：mallory 对一条带 `subject` 的事实，**根本不用 `supersedes`**，只是往同一个寄存器里
写了一条普通事实，受害者的 `trust` 就变成了 `superseded`。

而这条路径正是规则 4 自己在**上一句**认可为「正当替代方案」的那条（「第三方观察到陈旧，是
去反驳或者往寄存器里写」）。两句话不可能同时为真。

门控真正买到的是：**保护不在任何寄存器里的事实**。对那种事实，`supersedes` 是通往
`superseded` 的唯一路径。带 `subject` 的事实保护不了，也不可能保护 —— 寄存器是一片任何人
都能写的共享世界状态，这正是它成其为「共享」的原因。

已按实测重写规则 4 的理由（中英两版），并挑明对读者真正重要的后果：**在寄存器内部，
`superseded` 是关于寄存器的陈述，不是关于那条事实的陈述**；要判断内容可不可信，读者必须
去读 §8.3 的投票状态。向量零变化 —— 这是纯文字订正，语义未动。

### 4.2 结构性代价：规范从未说出口的那条

`fold-cost.ts` 的测量（单次调用，毫秒）：

| 事实数 | 堆(MB) | lifecycle | current | history | trust | descendants |
|---|---|---|---|---|---|---|
| 1,000 | 8 | 0.50 | 0.18 | 0.05 | 0.45 | 0.27 |
| 10,000 | 13 | 2.19 | 1.62 | 0.51 | 1.78 | 3.19 |
| 100,000 | 43 | 9.67 | 8.10 | 5.04 | 18.04 | 14.89 |

把两条规则放在一起：

- §8.0：**任何规范性结果都要求完整前缀**。
- §11.2：**压缩不得改变任何折叠结果** —— 因此它只回收 payload，永远不回收骨架。

推论是：**每一个合规读者都必须永久持有整条日志的骨架**，而且每回答一个问题就要全扫一遍。
一个读者对 N 条事实的日志回答 K 个问题，是 O(K·N) 的工作量，内存下界随日志年龄单调增长，
**协议里没有任何东西为它设界**。

这不是 bug —— 它是「总线无状态、含义住在读者里」这笔交易的价钱。但当时规范通篇没有提过它
一次：§2.3 的故障模型没有「读者资源耗尽」，§11 只谈总线侧的存储，想在长寿命部署里用它的人
必须自己发现这件事。

**已补进 §2.3**（中英两版）：作为「假设会发生、但不处理」的一条列出代价本身 —— 骨架地板随
日志年龄单调抬升且无界、单次提问 O(N)；随后给出三条不违反规范的缓解手段：增量折叠（§8 规定
的是答案不是算法，所以折叠可以建立在在线维护的索引上，单次提问降到答案本身的大小）、给派生
状态打检查点（私有派生数据，永不是事实；Δ 或 quorum 变了 MUST 丢弃重算）、以及按 subject
空间分成多条日志 —— 三条里只有最后一条降的是地板而不是工作量。§8.0 加了一句反向指引。
纯文字，向量零变化。

顺带一条实现自由度的说明：当前折叠全是全扫，但每一条都可以增量化（寄存器可维护每 subject
的最新成员、所有权可维护每目标的活跃集）。规范对增量实现只字未提，这是对的 —— 它规定的是
答案不是算法。但**参考实现选择了最朴素的那种**，任何认真的部署都需要自己重做这一层。

### 4.3 尾随分支：本轮未观察到分歧，不能因此说它不会发生

§8.4 的尾随过期分支依赖读者自己的墙钟，§9.3 明说它是仅供参考的、两个处在**同一前缀**上的
读者可以给出不同答案。本次验证里两个 auditor 恰好在这些状态上也一致 —— 装置照实记为
「恰好一致（并不被要求如此）」，而不是记成一条通过项。世界视图哈希**刻意只覆盖吸收态**
（`resolved`/`dead`）、寄存器和踪迹，把尾随态排除在外。

这是本次装置设计里最重要的一个决定：**如果把仅供参考的状态也塞进哈希，这个测试会间歇性
变红，而红的原因是规范允许的行为**。测试必须验规范说的话，不是验我希望它说的话。

### 4.4 harness 自己踩的两个坑（方法论）

两条都让结果**静默失效**而不是响亮失败，值得记下来：

**固定端口测的是「谁应答」。** `npx tsx` 在 orchestrator 与真正的服务之间隔了一个 shell 和
两个 node，杀掉自己持有的句柄未必杀得掉监听者。一个存活下来的总线应答了下一轮的健康检查，
那一轮就测了上一轮的日志 —— 事实数每跑一次翻倍（211 → 430 → 647 → 866），而**所有检查照样
全绿**。修法：每轮随机端口、进程组 detached、启动时若刚起的日志不是空的就拒绝继续。

这与 `dsh-antlegion/check.js` 要回答的是同一个问题。装置犯了它自己在别处已经修好的错。

**在不同 head 上比较折叠结果，等于测试本身违反了它要验的定理。** 第一版崩溃前折一次、崩溃
后再折一次比哈希，结果不同 —— 因为 harness 自己的探针在中间写了事实。§9.2 的边界恰恰说：
不同 `N` 上的两个读者可以不同，那是延迟不是分歧。只有把 head 钉住，这个比较才有意义。

## 五、结论

**协议本身在十二个真正隔离的进程下站得住。** 互斥、幂等、崩溃重分派、跨崩溃的确定性、
字段值域、折叠门控 —— 全部按规范所述发生，包括「总线接受一条它不该采信的事实」这种需要
两半分开成立的情形。

**当前实现有三处与规范不符，均已修复**，其中一处（Δ 不可配置）是「规范写了但代码没有入口」，
一处（`colony()`）是「规范写了但代码没做」，一处（规则 4 的理由）是「规范自己说过头了」。

**一处结构性代价规范从未说明**：完整前缀 + 只回收 payload 的压缩 ⇒ 读者内存无界增长。
这需要你决定是补进规范（推荐）还是留作实现常识。

**参考实现的折叠层是最朴素的全扫版本**，在 10⁵ 量级仍是毫秒级、可用；再上一个量级就需要
增量折叠。这不影响协议正确性，但影响「这东西能用在多大的世界上」这个问题的答案。
