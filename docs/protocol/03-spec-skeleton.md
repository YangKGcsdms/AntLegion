## 二、核心组织原则：字段的两个域

现有 §1 把九个字段平铺成一个 JSON 块，靠注释区分 `MUST` / `Set by bus` / `ADVISORY`。但字段真正的结构是**二分**的：

> **黑板上的一行字，由两个人写。**
> 作者写下内容；总线在旁边盖一枚骑缝章。

| | **作者域**（作者写入） | **总线域**（总线写入） |
|---|---|---|
| 字段 | `type` `author` `ts` `payload` `refs` `nonce` | `seq` `recv` `sig` |
| 进入内容哈希 | **是** | **否** |
| 可信度 | **不可信**（可伪造） | **可信**（总线签名） |
| 何时确定 | 追加之前 | 追加之时 |

这一条二分，把协议里最难讲清的四件事一次讲通：

| 问题 | 由二分直接给出的答案 |
|---|---|
| 为什么 `id` 只哈希一部分字段？ | 总线域必须在哈希之外。否则 `seq` 依赖 `id`、`id` 又依赖 `seq`，鸡生蛋 |
| 为什么重发会去重？ | 作者域相同 ⟹ `id` 相同 ⟹ 总线认出是同一条 |
| `nonce` 为什么存在？ | 它是作者**主动改变作者域**、以换取新 `id` 的唯一手段 |
| 为什么 `ts` 不可信而 `recv` 可信？ | 一个在作者域，一个在总线域。不是"建议用 recv"，而是**结构上只有 recv 可信** |

现文档把这四件事分散在四处各讲一遍；用这个二分，它们是同一条推论的四个推论。**这就是"规范"与"说明书"的区别：说明书逐条陈述规则，规范给出规则的生成结构。**

## 三、逐字段模板

每个字段一节，六栏 + 三段，缺一不可：

```
### 5.x  `字段名`

| 类型 | 写入方 | 必需性 | 进入内容哈希 | 可信度 |
|------|--------|--------|--------------|--------|

**语义。** 一句话。

**示例。** 具体值，最好嵌在一条真实事实里。

**设计依据。** 为什么必须这样；换一种设计会在哪一行崩掉。

**约束。** MUST / MUST NOT / SHOULD / MAY 逐条。
```

> **关于"设计依据"的写法**：用**反证**，不要用陈述。
> 不写"我们选择了两个时间戳"，而写"删掉任意一个，协议在哪一行崩掉"。
> 这是字段规范里信息量最高的形式——它同时告诉实现者：哪些可以妥协，哪些一动就全盘失效。

## 四、样章一：`ts` 与 `recv`（成对规范）

### 5.6 / 5.7　`ts` 与 `recv`

| | `ts` | `recv` |
|---|---|---|
| 类型 | number（unix 秒，含小数） | number（unix 秒，含小数） |
| 写入方 | **作者** | **总线** |
| 必需性 | MUST | 追加时由总线填入 |
| 进入内容哈希 | **是** | **否** |
| 可信度 | **仅供参考** | **可信** |

**语义。** `ts` 是作者*声称*事件发生的时刻。`recv` 是总线*见证*该事实到达的时刻。

**示例。** 一台时钟慢了 4 小时的机器发布构建失败：

```jsonc
{
  "type": "build.failed",
  "ts":   1748285600.0,   // 作者说：14:13（它的钟是错的）
  "recv": 1748300000.4,   // 总线见证：18:13（真实）
  "payload": { "job": "nightly", "exit": 1 }
}
```

**设计依据。** 两个时间戳看似冗余，删掉任何一个，协议都会坏：

- **只留 `ts`** —— 时间判定建立在可伪造的数字上。一个恶意的（或仅仅时钟漂移的）作者，把 `ts` 设成很久以前，就能让自己的领活**立即过期**从而绕开互斥；设成未来则能**永久霸占**一件活。**互斥失效**——而互斥是本协议的核心保证。
- **只留 `recv`** —— `recv` 不进内容哈希（否则鸡生蛋，见 §5.1），于是同一份内容重发会得到同一个 `id`，作者**永远无法表达"这是一次新动作"**。而且作者真正知道的事件时刻（日志行时间、文件 mtime）无处安放。**幂等与溯源同时失效。**

二者分工是刚性的：**`ts` 属于内容，`recv` 属于见证。**

**约束。**

- 作者 **MUST** 提供 `ts`。
- 总线 **MUST NOT** 因 `ts` 不合理而拒绝追加——总线不判断内容真伪（§2.2）。
- 总线 **MUST** 填入 `recv`，并将其纳入签名（§5.9）。
- 一切以时间为条件的折叠（领活超时 §8.1、TTL）**MUST** 以 `recv` 为准，**MUST NOT** 使用 `ts`。违反此条将破坏 §9.2 的确定性定理。
- 读者 **MAY** 向人展示 `ts`，但 **SHOULD** 标注其为作者自述。

## 五、样章二：完整实例的写法

第 6 节应当是**一整回合的事实序列**，逐条标注，把所有字段串起来。骨架如下（正式稿要把每条事实完整写出）：

| # | seq | 谁 | 事实 | 演示了什么 |
|---|---|---|---|---|
| 1 | 41 | `ci-bot` | `build.failed`，带 `payload` | 作者域 / 总线域的划分 |
| 2 | 42 | `agent-a` | `_.claim`，`refs.claim_of = #41` | 意图也是事实（推导第 2 步） |
| 3 | 43 | `agent-b` | `_.claim`，`refs.claim_of = #41` | 竞争；**42 < 43，A 胜** |
| 4 | — | `agent-b` | 读回、折叠、发现自己输了 | 无需通知：算出来的 |
| 5 | 44 | `agent-a` | `_.claim` 重发（同内容） | **去重**：返回既有 `id`，不产生新 seq |
| 6 | 45 | `agent-a` | `_.claim` + 新 `nonce` | **续期**：新内容 ⟹ 新 `id` ⟹ 新 seq |
| 7 | 57 | `agent-a` | `fix.done`，`refs.parent = #41`、`refs.resolves = #41` | 因果 + 解决 |
| 8 | — | 任意读者 | 折叠出：#41 已解决，归 `agent-a` | 确定性 |

再补一条**失败分支**：若 A 在第 6 步后崩溃，第 45 条领活在 `recv + Δ` 后过期，B 的下一次领活成为最小存活 seq——**演示推导第 7、8 步**。

这张表把九个字段、三条折叠、两个定理全部串在一个可读的故事里。它应当是整份规范中读者最先读、也最常回看的一节。

## 六、施工顺序

| 阶段 | 内容 | 风险 |
|---|---|---|
| **一** | 新增 §2 系统模型、§9 性质与证明、§13 相关工作；重写 §3 黑板与事实、§4/§5 全部字段、§6 完整实例、§7 操作时序 | 低——全是新增或改写非规范性内容 |
| **二** | §8 折叠语义：语义不变，改为论文体例，补不变式与状态转移表 | **中**——这是规范性内容，任何措辞改动都可能改变一致性判定，须逐条对照现行实现与 `conformance/vectors.json` |

阶段二必须遵守仓库既定规则：改动折叠规则即为**破坏线格式**，须同步 `PROTOCOL.md`、`conformance/vectors.json` 与跨语言校验器，并在提交信息中声明 `[protocol-change]`。**若只是重新表述而不改变语义，则 `vectors.json` 不应有任何变化——这正好是一道自检：向量变了，说明你不小心改了语义。**
