# mock colony —— 十二个隔离进程对着一条日志

```bash
npx tsx examples/mock-colony/colony.ts            # 跑一轮；全部通过才 exit 0
npx tsx examples/mock-colony/colony.ts --verbose  # 带上每个 agent 自己的日志行
npx tsx examples/mock-colony/fold-cost.ts         # 一个规范性答案要花读者多少代价
```

## 为什么需要它

那四个 `scenario-*.ts` 确实走了真实 HTTP，但所有客户端跑在**同一个 Node 进程**里 ——
一个事件循环、一个时钟、一个 fetch 栈、一个崩溃域。而协议的核心主张恰恰是关于「什么都不
共享的 agent」，所以那些场景验不了它：共享的事件循环把协议承诺去仲裁的东西提前串行化了。

这个 harness 把每个 agent 拉成**独立的操作系统进程**，只告诉它两件事：总线 URL，和它自己
的名字。没有 agent 拿到任务清单、同伴名单、阶段表或停止信号。

这轮跑的**阶段本身就是日志上的一个 subject 寄存器**，每个 agent 自己折叠出来。也就是说
harness 是照协议说的方式做协调的 —— 如果那不成立，这个 harness 根本跑不起来。

## 这个蚁群

| 个数 | 角色 | 干什么用的 |
|---|---|---|
| 4 | `worker` | 争抢 24 个任务；claim → 干活 → resolve；每个都逐字节重发一次自己的 claim |
| 2 | `sensor` | 写并修订 subject 寄存器 |
| 2 | `auditor` | 冷读者；把整个世界折成一个 sha256 |
| 1 | `crasher` | 拿下两个 claim，然后握着它们死掉 |
| 1 | `mallory` | 攻击者：五条格式非法的事实，四条需要门控的事实 |
| 1 | `retractor` | 把自己的寄存器头部收回去 |
| 1 | `chainer` | 一条 5 层因果链，外加一个 parent 永远不会到达的叶子 |

Δ 设为 4 秒（`ANTLEGION_CLAIM_TIMEOUT`），这样一次领取失效在短跑里就能观察到；日志用逐条
`fsync`，让崩溃测试是精确的。

## 它检查什么

| § | 主张 | 怎么把它置于危险中 |
|---|---|---|
| §9.1 | 互斥性 | 5 个 agent 抢 24 个任务。两个 agent 都认定自己赢了同一个任务，就是失败 |
| §8.4 §9.3 | 崩溃重分派、吸收态 | crasher 握着 claim 死掉；这些 claim 必须失效并由别人完成，而一次真实的 resolve 绝不能被撤销 |
| §9.4 | 幂等性 | 每个 worker 重发自己的 claim；总线必须返回同一个 `seq` 并标记 `deduped` |
| §5 | 字段值域 | 非有限 `ts`、非法 `type`、空 `refs` 值、两个生命周期 ref、数组 payload —— 全部必须被拒 |
| §10.1 | 折叠门控 | 陌生人的墓碑、陌生人的 supersede、对从未被领取事实的 resolve、从未持有过的 release。**总线四条全收** —— 它不判断含义 —— 而读者必须一条都不采信 |
| §8.1 | 寄存器 | 被撤回的头部折叠为 `null`，绝不回到上一个值 |
| §8.2 | 踪迹 | 未解析的祖先必须以显式缺口标记呈现 |
| §9.2 §11.1 | 跨崩溃的确定性 | SIGKILL 总线、从日志重放、再折叠**同一个钉住的前缀** |

## harness 自己踩出来的两个坑

记在这里，是因为它们很容易重犯，而且它们让结果**静默失效**而不是响亮地失败。

**固定端口测的是「谁应答」。** `npx tsx` 在 orchestrator 和真正的服务之间隔了一个 shell 和
两个 node 进程，所以给自己持有的那个子进程句柄发信号，未必杀得掉真正在监听的那个。于是一个
存活下来的总线应答了**下一轮**的健康检查，那一轮就心安理得地测了上一轮的日志 —— 事实数每跑
一次翻一倍，而所有检查照样全绿。修法是：每轮随机端口、进程组 detached、启动时若刚起的日志不
是空的就拒绝继续。这正是 `dsh-antlegion/check.js` 在把 agent 指向某个总线之前要问的那个问题。

**在不同 head 上比较折叠结果，等于什么都没测。** 第一版是崩溃前折一次、崩溃后再折一次然后
比哈希 —— 结果不一样，因为 harness 自己的探针在这中间往日志里写了事实。§9.2 的边界说的正是
这件事：处在不同 `N` 上的两个读者可以不同，那是延迟，不是分歧。只有把 head 钉住、让两边回答
同一个问题，这个比较才有意义。

## 输出

每条检查打 ✓ 或 ✗，任何一条失败进程就以非零退出。不属于通过/失败的东西 —— 一个值得说出来的
测量值，或者一处规范与实测对不上的地方 —— 打在 `notes` 下面。
